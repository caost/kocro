# 크로스 플랫폼 매크로 텍스트 입력 방식 검토

## 목적

VIA 매크로 키보드에서 지정한 키를 누르면 macOS, Windows, Linux의 포커스된 앱에 미리 작성한 텍스트를 입력한다. 현재 한글 입력기가 활성화되어 있어도 결과 문자열이 바뀌지 않아야 하며, 매크로마다 별도 프로세스를 시작하는 방식에서 발생한 지연을 피한다.

## 현재까지 확인한 요구사항

- macOS, Windows, Linux를 지원한다.
- 사용 중인 키보드 장치를 구분하지 않는다.
- 트리거는 F13부터 F24까지 사용한다. F25는 공통 지원 범위에서 제외한다.
- 상주 프로그램은 등록한 트리거만 처리하고 일반 키 입력은 수집하지 않는다.
- 트리거마다 사용자가 작성한 고정 텍스트를 연결한다.
- 현재 입력 언어와 관계없이 동일한 Unicode 문자열을 입력한다.
- 매크로를 실행할 때마다 외부 프로그램이나 셸 프로세스를 새로 시작하지 않는다.
- 관리자 또는 root 권한을 기본 전제로 삼지 않는다.
- 실패했을 때 이전 클립보드나 잘못된 문자열을 입력하지 않는다.

## 핵심 제약

일반 키보드는 문자 자체가 아니라 HID 키 코드를 전송한다. 포커스된 앱에 어떤 문자가 입력되는지는 운영체제의 키보드 배열과 입력기가 결정하므로, VIA에서 영문 키 코드를 보내는 것만으로는 영어 입력을 보장할 수 없다.

프로그램이 입력 소스를 영어로 변경하고 VIA가 이어서 문자열을 입력하는 방식에도 실행 순서 문제가 있다. VIA는 입력 소스 변경 완료를 알 수 없으므로 고정 지연을 넣거나 키보드와 호스트 사이에 별도 응답 절차가 필요하다.

## 검토한 대안

| 대안 | 입력기 독립성 | 앱 호환성 | 지연 | 주요 문제 |
| --- | --- | --- | --- | --- |
| 영어 입력 소스를 선택한 뒤 VIA가 입력 | 중간 | 높음 | 낮음~중간 | 입력 소스 변경과 VIA 입력 사이의 순서를 보장하기 어렵다. |
| 클립보드에 기록한 뒤 붙여넣기 | 높음 | 높음 | 낮음 | 클립보드 히스토리·동기화에 텍스트가 남을 수 있다. |
| 프로그램이 Unicode 입력 이벤트 전송 | 높음 | 중간 | 낮음 | 운영체제별 API와 권한이 다르고 일부 앱이 합성 입력을 거부한다. |
| 접근성 API로 입력 필드 값 변경 | 높음 | 낮음~중간 | 낮음 | 터미널·게임·캔버스 기반 UI 등에서 사용할 수 없고 권한 범위가 넓다. |
| QMK Raw HID 요청·완료 응답 | 높음 | 높음 | 낮음 | QMK 펌웨어 수정과 호스트 프로그램 구현이 모두 필요하다. |

## 현재 권장 방향

상주 프로그램이 F13~F24를 전역 단축키로 등록하고, 키에 대응하는 문자열을 메모리에 미리 읽어 둔다. 트리거를 받으면 운영체제별 어댑터가 포커스된 앱에 문자열을 직접 입력한다.

```text
VIA 키보드
  └─ F13~F24
        ↓
상주 프로그램
  ├─ 트리거 등록
  ├─ 고정 문자열 조회
  ├─ 운영체제별 직접 입력
  └─ 호환되지 않으면 허용된 방식으로 폴백
```

운영체제별 기본 구현 후보는 다음과 같다.

| 운영체제 | 기본 입력 방식 | 예상 폴백 | 제한 |
| --- | --- | --- | --- |
| Windows | `SendInput`과 `KEYEVENTF_UNICODE` | 클립보드 붙여넣기 | 더 높은 무결성 수준으로 실행된 앱, 보안 데스크톱과 일부 게임에는 입력할 수 없다. |
| macOS | `CGEvent`와 Unicode 문자열 지정 | 클립보드 붙여넣기 | Accessibility 권한이 필요하며 일부 앱은 이벤트의 Unicode 문자열을 무시할 수 있다. |
| Linux X11 | 합성 키 입력 또는 클립보드 붙여넣기 | 클립보드 붙여넣기 | 직접 Unicode 입력을 일관되게 제공하는 공통 API가 부족하다. |
| Linux Wayland | 클립보드 붙여넣기 또는 승인된 입력 제어 인터페이스 | 환경별 처리 | 컴포지터가 일반 프로그램의 임의 입력 생성을 제한한다. |

사용자에게는 하나의 동작으로 보이지만, 내부 구현은 운영체제별로 다르게 유지한다. Windows와 macOS에서는 직접 Unicode 입력을 우선 검토하고, Linux에서는 지원 범위에 따라 클립보드 붙여넣기를 기본값으로 사용할 수 있다.

## 보안 경계

상주 프로그램은 다음 범위를 넘지 않도록 설계한다.

- F13~F24만 등록하고 일반 키 입력을 수집하지 않는다.
- 프로그램 설정에 미리 저장된 문자열만 입력한다.
- 트리거 이벤트나 외부 프로세스가 전달한 임의 문자열을 실행하지 않는다.
- 셸 명령 실행, 플러그인 로딩, 네트워크 통신을 제공하지 않는다.
- 관리자 또는 root 권한으로 실행하지 않는다.
- 입력 문자열, 활성 앱과 기존 클립보드 내용을 로그에 남기지 않는다.
- 설정 파일은 현재 사용자만 읽고 쓸 수 있게 한다.
- 관리자 앱, 잠금 화면, 보안 입력창처럼 지원하지 않는 대상에서는 실패로 처리한다.
- 비밀번호, API 키와 인증 토큰은 매크로 문자열에 저장하지 않는다.

프로그램이 입력 이벤트를 생성할 수 있다는 사실 자체는 중요한 권한이다. 프로그램이 침해되면 공격자가 포커스된 터미널이나 앱에 명령을 입력할 수 있다. 따라서 자동 업데이트나 외부 확장 기능을 나중에 추가한다면 별도의 보안 검토가 필요하다.

## 클립보드 폴백 정책

클립보드 방식은 앱 호환성이 높지만 민감한 데이터가 클립보드 관리자, 운영체제 히스토리나 장치 간 동기화에 남을 수 있다. 폴백을 제공한다면 다음 조건을 적용한다.

- 기본적으로 기존 클립보드를 읽거나 백업하지 않고 지정 문자열로 덮어쓴다.
- 클립보드 기록에 성공한 뒤에만 붙여넣기 이벤트를 보낸다.
- 자동 삭제를 제공한다면 현재 클립보드가 해당 매크로 값 그대로일 때만 삭제한다.
- 사용자가 매크로 실행 뒤 새로 복사한 내용은 삭제하거나 복원하지 않는다.
- 민감한 문자열에는 클립보드 폴백을 허용하지 않는다.

## 실패 처리

- 등록되지 않은 키는 무시한다.
- 문자열 조회에 실패하면 아무 내용도 입력하지 않는다.
- 직접 입력이 일부만 성공할 수 있는 API라면 성공한 문자 수를 확인하고, 같은 문자열 전체를 자동으로 다시 입력하지 않는다.
- 직접 입력 실패 후 클립보드 폴백을 수행할지는 설정으로 명시한다. 자동 폴백은 중복 입력 가능성을 검토한 뒤에만 활성화한다.
- 프로그램 종료 시 등록한 전역 단축키와 입력 제어 리소스를 해제한다.
- 로그에는 오류 코드와 사용한 입력 방식만 남기고 문자열은 남기지 않는다.

## 검증 대상

다음 환경에서 트리거별 결과, 지연과 실패 동작을 확인해야 한다.

- 기본 텍스트 편집기
- Chromium 및 Firefox 입력 필드
- Electron 및 Java 기반 앱
- VS Code와 JetBrains IDE
- macOS Terminal, Windows Terminal과 Linux 터미널
- X11 및 주요 Wayland 컴포지터
- 원격 데스크톱과 가상 머신
- 관리자 권한 앱과 보안 입력창
- 한글 입력기가 활성화된 상태
- 여러 트리거를 연속으로 빠르게 누른 상태

측정 항목은 트리거 수신부터 마지막 문자 입력까지의 시간, 누락·중복 문자 수, 앱별 성공 여부와 요구 권한이다.

## 결정이 필요한 항목

- Linux 지원 기준을 X11까지로 제한할지, GNOME·KDE Wayland를 각각 지원할지
- 직접 입력 실패 시 클립보드 폴백을 자동으로 실행할지
- 여러 줄 텍스트와 특수문자·이모지를 지원할지
- 매크로 문자열을 일반 설정 파일에 저장할지, 운영체제 보안 저장소를 사용할지
- 트리거를 연속으로 누르면 순서대로 실행할지, 실행 중 새 요청을 거부할지
- 지원하지 않는 앱을 사용자에게 어떤 방식으로 알릴지

이 항목을 확정하면 합의된 요구사항을 새 `spec` 문서로 작성하고, 구현 순서는 별도 `plan` 문서에서 관리한다.
